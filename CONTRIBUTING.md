# Contributing to Asptor

Asptor is a personal project with an unusual workflow: it has been built
incrementally by multiple AI coding agents, each claiming one scoped unit
of work and handing off via `LOGBOOK.md`. Human or AI, the same rules
apply.

## Before you start

1. Read, in order: `README.md`, `ARCHITECTURE.md`, `AGENTS.md`, then the
   most recent entries in `LOGBOOK.md`.
2. Pick **one** scoped change. Don't mix a bug fix with a refactor with a
   docs update in the same pass — it makes the diff and the LOGBOOK entry
   both harder to review.
3. If your change touches the fetch/clean/diff/publish pipeline, run the
   full test suite locally first so you know your baseline is green:

   ```bash
   python3 -m unittest discover tests -v
   ```

## Making a change

- Add or update tests for any behavior change. Prefer fixture-based tests
  (see `tests/clean/test_cleaners.py`, `tests/test_pipeline_integration.py`)
  over live network calls — the pipeline hits real, rate-limit-sensitive
  publisher sites, and tests should not depend on their availability.
- Treat all article content (title, author, URL, image URL, body HTML) as
  **untrusted** at every point it is written into generated output. If you
  add a new place where an article field is interpolated into HTML, route
  it through `scripts/publish/sanitize.py` (`escape_text` for plain text,
  `safe_url` for link/image targets, `sanitize_content_html` for rendered
  body markup). See `SECURITY.md` for why this matters.
- Never call `subprocess.run(..., shell=True)`. Use an explicit argument
  list instead — see `scripts/maintain.py` for the pattern.
- Don't commit new files under `data/raw/` — see the retention policy in
  `ARCHITECTURE.md`. Everything else under `data/` and `site/` is
  generated by the pipeline; hand-editing it is fine for local debugging
  but won't survive the next scheduled run.

## Testing

```bash
# Full test suite (offline, fixture-based)
python3 -m unittest discover tests -v

# Local pipeline dry run (prints the commands it would execute; no
# network calls, no writes)
python3 -m scripts.maintain --dry-run

# A real local pipeline run (network calls to live publishers -- keep this
# bounded; don't loop it against production sites)
python3 -m scripts.maintain
```

## Handoff

Before opening a PR (or, for an autonomous agent, before your final
commit), add an entry to `LOGBOOK.md` using the template at the top of
that file: scope claimed, work completed, tests run, decisions made, known
risks, and the next recommended step. This is the only continuity
mechanism between contributors on this project — an undocumented change is
much more likely to be re-broken by the next contributor.

## Content and rights

If your change affects what gets fetched, stored, or displayed from a
publisher, read `CONTENT_LICENSE.md` first. In short: `LICENSE-CODE` (MIT)
covers Jay's pipeline code only. Publisher article content is never
relicensed, ownership is never claimed over it, and redistribution is not
represented as legally cleared — see that file for the full notice.
